# Rust static provenance: using compiler ownership facts to enrich rr dataflow answers

Scope: what rustc knows at compile time about moves, copies, borrows, drops and places; how to get it out in late 2026 (rustc ~1.97); how to join it with a machine-level rr trace (Pernosco-style dataflow) so "hopper" can say "moved from `a` into `b` at line 12" instead of "memcpy from X". ## 1. What MIR exposes, and how MIR maps to machine code

### Takeaway
MIR has exactly the vocabulary hopper wants: places with projections (`_3.f`, `*_3`), operands that are explicitly `copy` or `move`, `&`/`&mut` borrow rvalues, `StorageLive`/`StorageDead`, drop terminators, a lexical source-scope tree that records MIR inlining (callee `Instance` plus call-site span), and `var_debug_info` linking user variable names to places. None of that survives into DWARF as event kinds; only spans (as line-table rows and inlined-subroutine scopes) and variable locations survive. So the join must go MIR statement → span/scope → DWARF line row/inline frame → PC range, and it is only precise at `-O0`/low `mir-opt-level`; in release builds MIR optimisations (CopyProp, GVN, DestinationPropagation, ref_prop, MIR inliner) and LLVM rewrite or erase the moves themselves.

### Cited Findings
- A place "is an expression like `_3`, `_3.f` or `*_3` – it denotes a location in memory"; projections such as field `f` or `ProjectionElem::Deref` "project out" from a base place. — [rustc dev guide, MIR](https://rustc-dev-guide.rust-lang.org/mir/index.html)
- An operand is a constant, `copy Place` or `move Place`; copying requires the type to implement `Copy`, moving works for a place of any type. — [rustc dev guide, MIR](https://rustc-dev-guide.rust-lang.org/mir/index.html)
- Borrows are rvalues of the form `& (mut)? <Place>`. — [rustc dev guide, MIR](https://rustc-dev-guide.rust-lang.org/mir/index.html)
- `StorageLive(_1)` marks a local live until `StorageDead(_1)`; "These 'storage statements' are used by LLVM to allocate stack space." — [rustc dev guide, MIR](https://rustc-dev-guide.rust-lang.org/mir/index.html)
- `debug <Name> => <Place>;` annotations (var_debug_info) describe "a named user variable, and where (i.e. the place) a debugger can find the data"; `scope N { .. }` blocks describe lexical structure; MIR dumps annotate each statement with `// in scope 0 at src/main.rs:2:9: 2:16`. — [rustc dev guide, MIR](https://rustc-dev-guide.rust-lang.org/mir/index.html)
- Unoptimised MIR can be viewed on nightly with `-Z mir-opt-level=0 --emit mir`; the playground shows optimised MIR. — [rustc dev guide, MIR](https://rustc-dev-guide.rust-lang.org/mir/index.html)
- `SourceScopeData` has fields `span`, `parent_scope`, `inlined: Option<(Instance, Span)>` ("the root of a scope tree of another body, inlined into this body by the MIR inliner. `ty::Instance` is the callee, and the `Span` is the call site"), `inlined_parent_scope` and `local_data`. — [rustc_middle docs, SourceScopeData](https://doc.rust-lang.org/nightly/nightly-rustc/rustc_middle/mir/struct.SourceScopeData.html)
- Rustc "inspects MIR" and passes source, symbol and type information to LLVM, which emits DWARF (gnu targets) or PDB/CodeView (msvc targets); rustc's debuginfo is "very similar to that of C++". — [rustc dev guide, debuginfo intro](https://rustc-dev-guide.rust-lang.org/debuginfo/intro.html)
- MIR optimisation passes rewrite locals and have had debuginfo bugs: PR #147525 (October 2025) fixed statement debuginfo not being remapped during `ref_prop` and `dest_prop`, which "may also mix different debugging variables". — [rust-lang/rust PR #147525](https://github.com/rust-lang/rust/pull/147525); MIR test showing DestinationPropagation remapping debuginfo locals — [tests/mir-opt/debuginfo/dest_prop.rs](https://rust.googlesource.com/rust-lang/rust/+/HEAD/tests/mir-opt/debuginfo/dest_prop.rs)
- Older DestinationPropagation was gated to higher mir-opt levels "because we don't fix up debuginfo and remove storage statements" (historical, Fuchsia mirror of rustc source, pre-2022). — [dest_prop.rs (old mirror)](https://fuchsia.googlesource.com/third_party/rust/+/57e8fc56852e7728d7160242bf13c3ab6e066bd8/compiler/rustc_mir/src/transform/dest_prop.rs); a later merge note says it was being enabled by default — [source mirror log](https://git.dreamy.place/mirrors/rust/log/tests/mir-opt?showmsg=1) (could not confirm which stable release).
- "Remove fewer Storage calls in CopyProp and GVN" (PR #142531) changed those passes to keep more storage markers. — [rust commit 8da2d28](https://rust.googlesource.com/rust/+/8da2d28cbd5a4e2b93e028e709afe09541671663)
- Robert O'Callahan (Pernosco): "Rust optimized builds are hard to debug — LLVM optimization passes lose track of variables" (already in prior notes). — [Rust-Pernosco slides](https://robert.ocallahan.org/assets/images/Rust-Pernosco.pdf)
- Variable values can be missing or wrong "even at -O1 or -Og", and many such violations are compiler bugs (C/C++ study, 2023). — [Assaiante et al., "Where did my variable go?" 2023](https://iris.uniroma1.it/retrieve/79a790b2-ccd4-47f3-a5d9-f6a3868979f8/Assaiante_Where_2023.pdf)

### Inferences
- MIR is the right level: borrowck and drop elaboration run on it, so "move vs copy vs borrow vs drop" is explicit there and nowhere else. HIR/THIR lack the explicit moves; LLVM IR has only `memcpy`/loads/stores.
- The join key cannot be the MIR statement itself, because codegen does not emit an id per statement. The only survivable key is (span, inline scope chain), which DWARF carries as line-table rows (file:line:column) and `DW_TAG_inlined_subroutine` trees. Two MIR statements on the same span (common: `let b = a;` produces a move and storage markers on one span) are indistinguishable by PC alone; the sidecar must therefore carry *ordered lists* of events per span, and the debugger disambiguates by the observed machine effect (which bytes were copied, from which variable's DWARF location to which).
- At `-O0` (debug profile, `mir-opt-level=1` default in debug builds per my understanding, see Gaps) moves are usually lowered as `memcpy`/loads+stores of the whole place inside the PC range of the statement's span, and the source and destination locals have stable stack slots in DWARF. That is the regime where "this memcpy at PC p is the `move _3` into `_5` of `let b = a;` at line 12" is reliably recoverable.
- In release builds a move often produces *no* machine copy at all (the destination is the same slot, or the value stays in registers). That is not a failure for provenance: the answer is "same bytes, renamed from `a` to `b` at line 12", which the sidecar can supply when it knows that `b`'s var_debug_info place is derived from `a`'s via a move, even when the machine trace shows nothing. The sidecar must be computed on the *final optimised MIR* (the one codegen sees), not on borrowck MIR, or its places will not match DWARF variables.

### Gaps
- I did not find a source documenting exactly how codegen turns MIR `SourceInfo` into LLVM `DILocation`s (rustc_codegen_ssa `mir/debuginfo.rs`); the claim that each statement's span becomes the debug location of the instructions generated for it is background knowledge, not verified this pass.
- Default `mir-opt-level` per profile (I believe 1 in debug, 2 in release) not confirmed with a source this pass.
- No source found measuring how often moves survive as identifiable copies in release Rust.

## 2. Ways to get MIR or analysis facts out of rustc in 2026, and which toolchains they need

### Takeaway
Everything that reads MIR needs nightly (or `RUSTC_BOOTSTRAP`) plus the `rustc-dev` component; nothing works on a plain stable toolchain. `rustc_public` (ex-Stable MIR) is the forward path but as of 2026-11-01 is still not on crates.io and has no stable initialisation; `rustc_plugin` 0.15 (pinned `nightly-2026-05-01`, rustc 1.96) is the most practical cargo-wrapper framework today; Flowistry is usable as a library but its released analysis lags (MSRV 1.73 per README, crate last released 2025-09); Charon is beta, JSON, and too lossy for PC mapping; `-Z nll-facts` dumps per-function Polonius relations as TSV.

### Cited Findings
- rustc_public is "a public, SemVer compliant interface rather than a completely stable API"; it needs a nightly with the `rustc-dev` and `llvm-tools` components, `#![feature(rustc_private)]` and `extern crate rustc_public;`; the book's example pins `nightly-2025-10-27`. — [rustc_public book](https://rust-lang.github.io/rustc_public/print.html)
- There is "no stable way to initialize the compiler yet"; the unstable `run!(args, callback)` runs the callback after analysis and before codegen; `run_with_tcx!` also passes `TyCtxt` for internal APIs; rustc_public objects are only valid inside the callback and must not cross threads; `-Z always-encode-mir` gives dependency MIR. — [rustc_public book](https://rust-lang.github.io/rustc_public/print.html)
- A crates.io release is planned "in the near future" (tracking issue #30). — [rustc_public book](https://rust-lang.github.io/rustc_public/print.html); crates.io API on 2026-11-01 returns "crate `rustc_public` does not exist" (command: `curl https://crates.io/api/v1/crates/rustc_public`, run in this session). The 2025H1 project goal listed "publish the first version of StableMIR on crates.io". — [Rust project goal 2025h1: stable-mir](https://rust-lang.github.io/goals/2025h1/stable-mir.html)
- rustc_public is used by third-party compilers, e.g. NVIDIA's cuda-oxide documents it and expects it to be published on crates.io eventually. — [cuda-oxide docs](https://nvidia.github.io/cuda-rust/cuda-oxide/compiler/rustc-public.html); Kani is the reference migration guide — [rustc_public book](https://rust-lang.github.io/rustc_public/print.html)
- `rustc_plugin` is "a framework for writing plugins that integrate with the Rust compiler", a generalisation of Clippy's cargo integration: a CLI binary (`cargo <name>`) plus a driver binary; it forwards CLI args, sets the sysroot, finds the crate for a file and handles dependencies. Each release pins one nightly and a nightly change is a breaking change: v0.15 → `nightly-2026-05-01` (rustc 1.96), v0.14 → `nightly-2025-08-20` (1.90), v0.13 → `nightly-2025-03-03` (1.86), v0.7 → `nightly-2023-08-25` (1.73). Each version has a maximum supported Rust version. MIT licence. — [rustc_plugin README](https://github.com/cognitive-engineering-lab/rustc_plugin)
- crates.io (queried 2026-11-01): `rustc_plugin` and `rustc_utils` latest `0.15.2-nightly-2026-05-01`, published 2026-05-03; `flowistry` latest `0.5.44`, published 2025-09-23 (previous 0.5.42 on 2024-07-29); `charon` on crates.io is only a 2019 `0.0.0` placeholder. — [crates.io rustc_plugin](https://crates.io/crates/rustc_plugin), [crates.io rustc_utils](https://crates.io/crates/rustc_utils), [crates.io flowistry](https://crates.io/crates/flowistry)
- Flowistry: "a static analysis tool for Rust that tracks information flow", shipped as a VS Code "focus mode"; README states a maximum supported Rust version of 1.73 and an install nightly of `nightly-2023-08-25` with `rust-src`, `rustc-dev`, `llvm-tools-preview`; docs hosted off docs.rs because docs.rs does not support `rustc_private` crates. — [Flowistry README](https://github.com/willcrichton/flowistry). Note the README's MSRV (1.73) conflicts with the newer 0.5.44 crate release (2025-09, which by version alignment likely tracks rustc_plugin 0.14 / nightly-2025-08-20); I could not confirm the crate's pinned nightly.
- Flowistry limitations stated by its README: interior mutability not fully handled (e.g. `Arc<Mutex<T>>` writes via `x` not seen as mutating `y`); callee bodies not analysed (type signatures only, so `&mut self` methods are assumed to modify the receiver); "not all source code maps cleanly to MIR"; analysis limited to the smallest enclosing function (closures, nested fns, async not analysed together). — [Flowistry README](https://github.com/willcrichton/flowistry)
- Charon exports a crate and its dependencies as JSON (`crate_name.llbc`), including types, functions, traits, impls, globals, "simplified MIR bodies" and per-item source information; readable via `charon_lib::export::CrateData` (Rust) or `charon-ml` (OCaml); it calls itself "beta software" with planned breaking API changes; Apache-2.0. — [Charon README](https://github.com/AeneasVerif/charon)
- `-Znll-facts` (nightly) writes one directory per function of tab-separated `.facts` files holding the Polonius input relations, with points like `Start(bb0[5])` and variables like `_1`. — [vyre-libs rustc_facts.rs (third-party loader)](https://docs.rs/crate/vyre-libs/0.6.3/source/src/borrowck/rustc_facts.rs) (secondary source; I did not reach the Polonius book this pass).
- Aquascope (same lab) generates interactive visualisations of how the borrow checker reasons and how the program executes; its interpreter mode requires `cargo miri setup` and the `miri` + `rustc-dev` components on pinned `nightly-2024-12-15`; research software; paper: Crichton, Gray, Krishnamurthi, "A Grounded Conceptual Model for Ownership Types in Rust", OOPSLA2 2023, doi:10.1145/3622841. — [Aquascope README](https://github.com/cognitive-engineering-lab/aquascope)

### Inferences
- For hopper the choice is between (a) a `rustc_driver` `Callbacks` implementation wrapped by `rustc_plugin` (full internal MIR including `SourceScopeData.inlined`, `var_debug_info`, optimised MIR via `tcx.optimized_mir`/`instance_mir`, and access to the codegen-unit partitioning), and (b) `rustc_public` (smaller, SemVer-tracked, but its `run!` callback runs before codegen, its MIR surface is not documented in the book, and it is not on crates.io). Recommendation: build on `rustc_plugin` + `rustc_driver` now, pinned to the same nightly that cadabra3 can be built with; keep the extraction code behind a narrow internal trait so it can move to `rustc_public` when that is published with an initialisation API.
- Charon and Polonius facts are the wrong level for PC mapping: Charon simplifies MIR (loses the exact statement shape and drop/storage detail that codegen sees) and runs on pre-optimisation MIR; nll-facts describe loans and regions on borrowck MIR, which is before optimisation. Both are useful only as optional labelling ("this borrow was live here"), not as the join key.
- Flowistry is the one ready-made static "what influenced this place" analysis. It can be called from the same driver (it is a library over rustc_plugin's ecosystem) to produce per-function dependency sets used for pruning/labelling (section 4), but its intraprocedural and signature-only design means it must be treated as a hint, not ground truth.
- A "stable toolchain" story is possible only by building the user's crate twice: once normally on the user's stable toolchain for execution/recording, and once with the analysis nightly purely to emit the sidecar. That breaks the join unless the two builds produce identical MIR/spans, which is not guaranteed across rustc versions. So the recorded binary itself must be built by the pinned nightly (or with the sidecar emitted from the same `rustc` invocation that produced the binary). This is the decisive design constraint.

### Gaps
- `-Z dump-mir` output format and stability, MIRAI's maintenance status, Kani's current use of rustc_public, and cargo-careful's relevance were not checked with sources this pass (cargo-careful builds std with debug assertions; it is not an analysis-extraction tool, from background knowledge only).
- rustc_public's exposed MIR types (whether `Operand::Move`, `Rvalue::Ref`, `StatementKind::StorageLive`, `SourceInfo.scope`, `var_debug_info` and inlined scope data are all present) are not documented in the fetched book; needs a read of `compiler/rustc_public/src/mir/body.rs` at the pinned nightly.
- rustc_public tracking issue #30 could not be read (GitHub API returned nothing for the repo names tried).
- Whether Flowistry 0.5.44 builds against rustc_plugin 0.14/0.15 was not confirmed.

## 3. What rustc's DWARF does and does not say about moves, ownership and lifetimes

### Takeaway
DWARF from rustc encodes types (including Rust enums via `DW_TAG_variant_part`, with niche-encoded discriminants, or a C++-like scheme for MSVC), variable locations/location lists, lexical blocks and inlined subroutines. It encodes no move, borrow, drop, lifetime or "moved-out" state; a moved-from local keeps a valid-looking location and shows stale bytes. No accepted Rust project goal for 2025H2 targets richer ownership debuginfo. A sidecar is therefore required; DWARF cannot carry this today without vendor extensions.

### Cited Findings
- rustc's enum debuginfo has two backends, `native` and `cpp_like`, chosen by `cpp_like_debuginfo`/`wants_c_like_enum_debuginfo`; layouts are distinguished by `rustc_abi::Variants` and `TagEncoding` (direct vs niche tag); C-style enums become `DW_TAG_enumeration_type`; coroutine states get their own variant structs; `compute_discriminant_value` maps variant index to discriminant. The module is private (an internal detail that can change between nightlies; page is nightly 1.101.0). — [rustc_codegen_llvm debuginfo/metadata/enums](https://doc.rust-lang.org/nightly/nightly-rustc/rustc_codegen_llvm/debuginfo/metadata/enums/index.html)
- Niche-optimised enum debuginfo has a history of breaking pretty-printers. — [rust-lang/rust #53153](https://github.com/rust-lang/rust/issues/53153) (from prior notes)
- gdb "is normally at the mercy of the debuginfo that the compiler creates"; rustc emits lexical blocks to explain variable scopes. — [gdb bugzilla 31079](https://inbox.sourceware.org/gdb-prs/bug-31079-4717-qGhJwfrbjC@http.sourceware.org%2Fbugzilla%2F)
- A DWARF location relative to the frame can go stale (e.g. after an epilogue resets SP) and gdb "has no good way to know where a location ends", so the compiler must provide it. — [gdb-patches, Tromey](https://inbox.sourceware.org/gdb-patches/87ee34lla9.fsf@tromey.com/)
- 2025H2 Rust project goals (41 proposed, RFC 3849 merged 2025-09-09) mention debuginfo only as a side benefit of other goals (e.g. building std with debug information); no standalone debuginfo goal appeared in the results. — [Project goals for 2025H2](https://blog.rust-lang.org/2025/10/28/project-goals-2025h2), [2025h2 goal list](https://rust-lang.github.io/rust-project-goals/2025h2/goals.html)
- CodeView "dates to 1985 and was designed for C", so many workarounds exist; GDB has full native Rust support, LLDB partial, CDB none (as of November 2025). — [rustc dev guide, debuginfo intro](https://rustc-dev-guide.rust-lang.org/debuginfo/intro.html)

### Inferences
- "Moved-out" is invisible in DWARF: after `let b = a;` with `a: String`, `a` stays in scope with the same location, and its bytes are typically unchanged (a move is a bitwise copy; the source is just not dropped). A debugger shows `a` as a live, valid string. The sidecar's `move` events let hopper grey out `a` after the move PC and say "moved into `b` at line 12" instead.
- The location of a local after `StorageDead` is likewise not ended in DWARF if the location covers the whole scope; the sidecar's StorageDead events give hopper a second, compiler-sourced end-of-life point.
- Niche enums matter for provenance because a write to the niche field *is* the discriminant write; hopper's value view must use rustc's variant_part/discr description, and a dataflow step that changes only niche bytes should be reported as "variant changed to `None`", not as a field write.
- The cleanest long-term option would be an upstream rustc `-Z` flag emitting ownership events (keyed by the same `DILocation`s) as a sidecar section; that is a proposal hopper could make once a prototype exists. Nothing like it exists today in the sources found.

### Gaps
- I did not find any rustc/LLVM proposal or Rust project goal (2025H2 or 2026H1) for encoding moves or lifetimes in debuginfo; the 2026H1 goal list was not checked.
- I did not find whether rustc enables LLVM assignment tracking (`#dbg_assign`), which would improve variable locations in optimised code.
- No primary source found on the debuginfo working group's current status.

## 4. Static information-flow and slicing for Rust, and using a static slice to prune or label a dynamic slice

### Takeaway
Flowistry shows that Rust ownership types let an intraprocedural analysis soundly approximate information flow through calls from the callee's signature alone, matching whole-program results in 94% of cases. Hybrid slicing (Gupta, Soffa, Howard 1995/1997) shows how static slices are refined with runtime data (breakpoints, dynamic call graph). For hopper the direction is reversed: the dynamic trace is exact for what happened, and the static facts supply *meaning* (move/clone/borrow labels, which source place) and *pruning* (skip copies that the static analysis says cannot carry the queried value).

### Cited Findings
- Flowistry (Crichton, Patrignani, Agrawala, Hanrahan, PLDI 2022): ownership types let information flow through calls be analysed soundly and precisely "using only the callee's type signature", without whole-program source; soundness proved as noninterference on the Oxide model of Rust; "modular flows are identical to whole-program flows in 94% of cases"; prototypes of a program slicer and an IFC system were built on it. — [arXiv 2111.13662](https://arxiv.org/abs/2111.13662)
- Flowistry practical limits (interior mutability, signature-only calls, smallest enclosing function, not all source maps to MIR). — [Flowistry README](https://github.com/willcrichton/flowistry)
- Hybrid slicing uses breakpoint information and the dynamic call graph; breakpoints and call/return points split the path into intervals; the hybrid slice is more precise than a static slice and cheaper than a dynamic slice; slices shrink as more breakpoints are added; intraprocedurally it degenerates to static slicing without breakpoint information. — [Gupta & Soffa, FSE 1995](https://homes.cs.washington.edu/~mernst/teaching/6.893/readings/gupta-fse95.pdf); [Gupta, Soffa, Howard, TOSEM 6(4) 1997](https://www.cs.ucr.edu/~gupta/research/Publications/Comp/hybrid-gupta.pdf)
- Precise dynamic slicing algorithms and their cost are surveyed by Zhang, Gupta et al. — [Zhang, Gupta, Zhang, TOPLAS 2004 (PDF)](https://www.cs.purdue.edu/homes/xyzhang/Comp/toplas04a.pdf)

### Inferences
- Labelling (the main win): each backward dataflow step in the machine trace (a store, a register copy, a `memcpy`) is looked up by PC → (span, inline chain) → sidecar events at that span. If one event is `move src→dst`, `copy`, `clone call`, `field projection`, `deref` or `drop`, the step is relabelled with source places, collapsing many machine steps into one source-level hop ("`b` ← move `a`, line 12"). This is exactly Pernosco's "skip trivial copies" heuristic, but with compiler-given rather than heuristic boundaries ([Pernosco dataflow](https://pernos.co/about/dataflow/) states Rust's frequent moves make copy-skipping especially valuable).
- `Clone` is a call, not a copy: the sidecar records `Call(Clone::clone, &src) -> dst` at that span, so when the dynamic chain enters `clone`'s body hopper can present it as "cloned from `config.name` at line 40" and continue backward into the source's history (the clone's bytes come from heap reads of `src`'s buffer).
- Pruning: when following a value backward through a function, Flowistry's per-function dependency set for the destination place bounds which earlier statements can matter; machine writes whose (span) is outside that set can be deprioritised in the UI (not discarded, because unsafe code, interior mutability and FFI break soundness).
- Ownership gives a soundness shortcut at the machine level too: after a `move`, the source place is dead for reads (borrowck guarantees it), so a backward search for "who last wrote these bytes of `b`" can stop at the move and switch to `a`'s history without scanning for aliased writers in between, except in unsafe code. This is a hypothesis to validate in the prototype.

### Gaps
- Flowistry paper details on how lifetimes bound alias sets were not extracted (only the abstract was fetched).
- No prior work found that labels a *dynamic* machine-level slice with *static* Rust ownership facts; this appears novel, but the search was not exhaustive.
- Tree Borrows / Stacked Borrows were not researched this pass; their notion of pointer provenance (tags) differs from hopper's "value origin" and is relevant only to unsafe code.

## 5. Prior art joining static compiler facts with dynamic traces, and debuggers with sidecar metadata

### Takeaway
Pernosco already does machine-level copy-following and highlights it as most useful for Rust, without compiler semantics. The RAD Debugger converts PDB/DWARF into its own RDI sidecar format, which shows the "debugger-owned derived debug format" pattern. Hybrid slicing is the classic static+dynamic join. I found no debugger that consumes Rust MIR ownership facts. Aquascope (static borrowck permissions plus a Miri-based interpreter view) is the closest Rust-specific join of static ownership facts with execution, but it runs on an interpreter, not on native traces.

### Cited Findings
- Pernosco dataflow: click a value to see where it came from; copies between memory/register locations are followed backward and trivial copy steps skipped; heuristics highlight important copies (e.g. writes to output buffers); "especially useful for Rust and some modern C++, which move data frequently"; follows data across processes via pipes and sockets. — [Pernosco dataflow](https://pernos.co/about/dataflow/)
- Pernosco builds its database by replaying rr recordings with binary instrumentation; 118K lines of Rust using gimli. — [Pernosco vision](https://pernos.co/about/vision/), [Rust-Pernosco slides](https://robert.ocallahan.org/assets/images/Rust-Pernosco.pdf)
- RAD Debugger: RDI is "our custom debug information format", parsed instead of PDB/DWARF; `rdi_from_pdb` converts PDB, `rdi_from_dwarf` is in progress; `radbin` converts and dumps RDI; the RAD Linker can emit RDI natively; alpha, Windows x64 with PDBs only. — [RAD Debugger repo](https://github.com/EpicGames/raddebugger), [v0.9.13-alpha release](https://github.com/EpicGamesExt/raddebugger/releases/tag/v0.9.13-alpha)
- CodeTracer exposes custom DAP requests including `ct/originChain` and has rr/TTD/MCR backends (from prior notes). — [ct-dap.md](https://github.com/metacraft-labs/codetracer/blob/main/ct-dap.md) (the URL returned 404 on 2026-11-01; the document may have moved).
- Aquascope visualises borrow-checker reasoning and execution, with a Miri-dependent interpreter mode. — [Aquascope README](https://github.com/cognitive-engineering-lab/aquascope)
- Hybrid slicing joins static slices with breakpoint/call-graph data. — [TOSEM 1997](https://www.cs.ucr.edu/~gupta/research/Publications/Comp/hybrid-gupta.pdf)

### Inferences
- RDI is the model for hopper's sidecar in one respect: the debugger owns a derived, indexed format and a converter, so DWARF parsing and MIR facts are merged once, offline, into a PC-keyed table rather than joined at query time.
- Aquascope's approach (Miri) cannot scale to a real rr recording of cadabra3, but its static permission view (which places are readable/writable/owned at each point) is the same fact family hopper would label with.

### Gaps
- Microsoft TTD's use of PDB data for value provenance was not researched this pass.
- CodeTracer's current Rust support and how `ct/originChain` computes origins could not be checked (404).
- Whether Pernosco internally uses any rustc-specific metadata is not public.

## 6. Recommended sidecar format and pipeline, and what breaks it

### Takeaway
Build a `cargo hopper-build` wrapper on `rustc_plugin` (pinned nightly) whose driver, in the same rustc invocation that produces the recorded binary, walks the *final optimised MIR of every codegen'd instance* (post-monomorphisation, post-MIR-inlining) and writes per-instance tables of ownership events keyed by (symbol, span, inline scope chain, statement order). Hopper joins these to PCs through DWARF line tables and `DW_TAG_inlined_subroutine` (gimli/addr2line), then disambiguates multiple events on one span by matching observed machine copies against DWARF locations of the source and destination places. Ship it debug-first (`-C opt-level=0`, `mir-opt-level` low), treat release builds as best-effort labels, and key the sidecar by a hash of the binary's build-id so stale sidecars are rejected.

### Cited Findings
- rustc_plugin provides the CLI-plus-driver split and cargo integration and pins one nightly per release. — [rustc_plugin README](https://github.com/cognitive-engineering-lab/rustc_plugin)
- `SourceScopeData.inlined` records each MIR-inlined callee `Instance` and call-site span. — [SourceScopeData docs](https://doc.rust-lang.org/nightly/nightly-rustc/rustc_middle/mir/struct.SourceScopeData.html)
- rustc_public's `run!` callback runs after analysis and before codegen, and objects are only valid inside it. — [rustc_public book](https://rust-lang.github.io/rustc_public/print.html)
- `-Z always-encode-mir` makes dependency MIR available. — [rustc_public book](https://rust-lang.github.io/rustc_public/print.html)
- gimli/addr2line are the standard Rust crates for DWARF line tables and inline frames (prior notes). — [crates.io gimli](https://crates.io/crates/gimli)
- MIR passes (dest_prop, ref_prop, CopyProp, GVN) rewrite locals and their debuginfo, and have had remapping bugs as late as October 2025. — [PR #147525](https://github.com/rust-lang/rust/pull/147525)

### Proposed design (inference; not sourced as existing practice)
Pipeline:
1. `cargo hopper-build` (rustc_plugin CLI) sets `RUSTC_WORKSPACE_WRAPPER` to `hopper-driver` for every crate including dependencies (and `-Z always-encode-mir` so generic instances from deps have MIR), and passes `-C debuginfo=2`, `-C force-frame-pointers=yes`, optionally `-Z mir-opt-level=0/1` and `-C opt-level=0/1`.
2. `hopper-driver` implements `rustc_driver::Callbacks`; after analysis it calls rustc's codegen-unit collection (`collect_and_partition_mono_items`) to list the exact `Instance`s this crate will codegen, and for each gets `instance_mir` (the optimised MIR that codegen lowers), substituting generics.
3. For each instance, it emits rows: `(instance symbol (mangled v0), bb, stmt_idx, span (file,line,col range), inline scope chain [(callee symbol, call-site span)…], event kind, src place, dst place, type, size)`, where kind ∈ {move, copy, borrow-shared, borrow-mut, reborrow (`&*p`), raw-addr-of, field/index/downcast projection (`Downcast` = enum variant), deref, drop (from `Drop` terminators after elaboration), storage-live, storage-dead, call (with `Clone::clone`/`ToOwned`/`From` flagged), aggregate construction, discriminant write}. Places are rendered with var_debug_info names (`config.name`, `(*self).buf`) plus the raw local path for machine matching. Types carry layout (field offsets) so a partial copy of bytes can be mapped to a field.
4. Output: one file per crate under `target/hopper/<crate>-<hash>.hsc`, a compact columnar binary (e.g. Cap'n Proto or a simple length-prefixed table with an interned string pool, mirroring RDI's approach), plus a link step that merges them and stamps the final binary's GNU build-id.
5. At index time hopper, for each PC in a dataflow step, resolves (symbol, line row, inline chain) with gimli/addr2line, finds candidate sidecar rows with the same symbol, span and inline chain, and selects among them by checking which row's src/dst places' DWARF locations at that PC match the addresses/registers the machine step read and wrote.

What breaks it, and mitigations:
- **Inlining.** MIR inlining is recorded in `SourceScopeData.inlined`, but LLVM inlining happens after the sidecar is written; LLVM preserves it only as DWARF inlined-subroutine entries. Mitigation: emit rows per *callee instance* too, and match an LLVM-inlined region by its DWARF `DW_AT_abstract_origin` symbol plus span.
- **Optimisation.** Moves can vanish (no machine copy), be merged (dest_prop), or turn into register moves; LLVM can reorder and spread one statement across many PCs, and line tables attribute instructions to the "wrong" span. Mitigation: mark every label with a confidence (exact at -O0; "span-matched" vs "location-matched" vs "inferred rename" in release), and fall back to raw Pernosco-style output when no row matches.
- **Generics and monomorphisation.** MIR is per generic item; machine code is per instance. Mitigation: key by instance symbol (v0 mangling), emit rows after substitution; shared generics (`-Z share-generics`) mean an instance may be codegen'd in another crate, so the merge step must dedupe by symbol.
- **Incremental builds and cache.** If a crate's object comes from the incremental cache, the driver still runs analysis but codegen of some CGUs is reused; the sidecar must be produced for every codegen'd instance regardless, or cached alongside the object keyed by the CGU hash. Simplest first version: disable incremental for hopper builds (`CARGO_INCREMENTAL=0`).
- **Toolchain coupling.** The sidecar is only valid for the exact rustc that built the binary; the recorded program must be built with the pinned nightly. Reject sidecars whose build-id does not match.
- **std/core.** Precompiled std has no sidecar unless built with `-Z build-std` under the driver; otherwise std frames show raw machine dataflow.
- **unsafe, FFI, interior mutability.** Ownership guarantees do not hold; labels still apply (they describe what MIR did) but the "move ends aliasing" pruning must be disabled in unsafe blocks and through `UnsafeCell`.
- **Async and closures.** Coroutine state machines move locals into generator fields (`Downcast`+field projections of the coroutine layout); the sidecar must map coroutine saved-local fields back to source variables, which rustc's coroutine layout records (background knowledge, not verified this pass).

### Gaps
- No existing tool found that emits a per-instance post-optimisation ownership table; the design above is untested.
- Whether `collect_and_partition_mono_items` and `instance_mir` are reachable from rustc_public (vs only internal rustc APIs) was not verified.
- How reliable column info in rustc line tables is (whether rustc emits columns by default) was not checked; column precision directly affects disambiguation of several events on one line.
- Cost of running the extra pass on a cadabra3-sized workspace (and sidecar size) is unmeasured; a first experiment should measure it on one cadabra3 crate built with the pinned nightly.

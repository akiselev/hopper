## Project-by-project architecture (modules, rr link, data model, query API, value extraction, tricks, copy/avoid)

### Takeaway
None of these projects is an open, Rust-native, rr-backed omniscient engine that hopper could adopt. CodeTracer has the
richest design: a Rust DAP server with about 55 `ct/*` extensions, a seekable chunked trace container, a tick-interval
materialization cache and origin chains. But its rr backend (`ct-native-replay`, in `codetracer-native-backend`) is a
separate, licence-gated binary whose source is not public, and the AGPL front end can only be learned from. midas and the
three MCP servers are thin wrappers around gdb over GDB/MI or gdb's Python API. BugStalker (MIT) has the best reusable
Rust value model for Rust types, but its evaluator reads memory through ptrace, so it would need a memory/register trait
cut into it. The RAD Debugger's evaluator shows the right abstraction: every read goes through a pluggable
"space read" hook, and a generation counter invalidates caches.

#### CodeTracer db-backend (Rust, AGPLv3)
- The crate is named `replay-server` (edition 2024). It depends on the trace-format crates by path (`codetracer_trace_types`, `_reader`, `_writer`, `codetracer_ctfs`), on `origin-classifier`, and on tree-sitter. Its build script compiles "the Nim MCR emulator's generated C output into the crate via cc::Build". Optional `wasm-bindgen`/`web-sys` features exist for a browser build — [CT src/db-backend/Cargo.toml](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/src/db-backend/Cargo.toml)
- Size and shape: about 165k lines of Rust across `src/` and `tests/`. The largest modules are `dap_handler.rs` (8,420 lines), `db.rs` (5,682), `ctfs_trace_reader/mod.rs` (5,300), `emulator_session.rs` (5,235), `dap_server.rs` (4,632), `expr_loader.rs` (3,701) and `task.rs` (3,689) (`wc -l` over the clone) — [CT src/db-backend/src](https://github.com/metacraft-labs/codetracer/tree/d29c0743b755bef5452f9dc4233f0e4a3deac50e/src/db-backend/src)
- **The backend abstraction is the `ReplaySession` trait.** Its methods: `load_location`, `run_to_entry`, `load_events`, `step(action, forward)`, `step_over_statement`, `load_locals`, `load_value(expression, depth_limit, lang)`, `load_return_value`, `load_step_events(step_id)`, `load_callstack`, `load_history`, `add_breakpoint(path, line, column, condition)`, the tracepoint methods, `jump_to(step_id)`, `jump_to_call`, `event_jump`, `callstack_jump`, `location_jump`, `evaluate_call_expression` and `recording_head`. A comment says `depth_limit` and `lang` are "currently … only used for rr!" — [CT src/db-backend/src/replay.rs](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/src/db-backend/src/replay.rs)

It talks to the worker over a Unix socket (TCP on Windows) — [CT src/db-backend/src/recreator_session.rs](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/src/db-backend/src/recreator_session.rs) (lines ~298–382)

The code names its source as `codetracer-native-backend`'s `src/licensing/cli.rs` — [CT recreator_session.rs](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/src/db-backend/src/recreator_session.rs)

The 26.10.1 notes say `ct-native-replay` "is discovered on PATH rather than bundled" — [CT CHANGELOG.md](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/CHANGELOG.md)

- **The worker wire protocol is `ReplayQuery`,** a serde enum tagged by `kind`: `RunToEntry, LoadLocation, Step{action,forward}, LoadLocals, LoadReturnValue, LoadValue{expression,lang,depth_limit}, AddBreakpoint{path,line}, …, LoadCallstack, LoadHistory, EventJump, CallstackJump, RestoreAt{geid,tid,tick,phase}, GetRecordingHead, SeekToGeid{geid}, SeekToTicks{ticks}, GetProcessInfo`. - The rr origin smoke test SKIPs unless `rr`, `ct-native-replay` and `gcc` are present, and notes that "the dev shell here does not have `rr` or `ct-native-replay`" — [CT src/db-backend/tests/origin_rr_smoke.rs](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/src/db-backend/tests/origin_rr_smoke.rs)
- **Backend mix in late 2026.** `ct record --backend` is valid as `mcr, rr` on Linux, and "MCR is the default on every host". `--backend rr` on macOS and `ttd` on Linux are refused (26.10.1) — [CT CHANGELOG.md](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/CHANGELOG.md). A legacy rr trace is recognised by an `rr/` subdirectory in the trace folder, written by `ct-native-replay record`, beside a CTFS `trace.ct` sidecar — [CT dap_server.rs `resolve_replay_trace_path`](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/src/db-backend/src/dap_server.rs) (~line 1693)
- **Materialized (non-rr) data model.** `Db` holds `functions`, `calls: DistinctVec<CallKey,DbCall>`, `steps: DistinctVec<StepId,DbStep>`, `variables: DistinctVec<StepId,Vec<FullValueRecord>>`, `types`, `events`, `paths`, per-step `compound`/`cells` maps, `cell_changes: HashMap<Place,Vec<CellChange>>`, `step_map: PathId → line → Vec<DbStep>` and `path_map` — [CT src/db-backend/src/db.rs](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/src/db-backend/src/db.rs)
- The call tree (`Calltrace`) keeps per-call `CallState{expanded, hidden_children, children_count}`. It "prefer[s] the SEEKABLE `calls.dat` path … decompressing only the chunks it touches" over a fully materialized `Db` — [CT src/db-backend/src/calltrace.rs](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/src/db-backend/src/calltrace.rs)
- "Flow" (values per line of the current function, omniscient) is computed by `flow_preloader` against `&mut dyn ReplaySession`: it places breakpoints, runs `step(Action::Continue)`, `jump_to_call` and `step(Action::StepIn)`, and reads `current_step_id`. For rr that means driving the replay — [CT src/db-backend/src/flow_preloader.rs](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/src/db-backend/src/flow_preloader.rs) (lines 341–601). `expr_loader.rs` parses source with tree-sitter to find the expressions and branches to show per line — [CT src/db-backend/src/expr_loader.rs](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/src/db-backend/src/expr_loader.rs)
- **Native symbol handling** (used by the MCR emulator path): `dwarf_index.rs` gives `DwarfIndex::resolve_pc`, mapping a PC to file, line, column and function, and `stack_unwinder.rs` gives multi-frame unwinding from `.eh_frame`/`.debug_frame` CFI with a memory-read callback, "deliberately decoupled" from the emulator's memory reader — [CT dwarf_index.rs](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/src/db-backend/src/dwarf_index.rs); [CT stack_unwinder.rs](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/src/db-backend/src/stack_unwinder.rs)
- The omniscient DB for MCR is an `OmniscientDb` trait over an FFI shim into Nim code (`write_log.nim`, `omniscient_query.nim`), reading the CTFS namespaces `memwrites.tc` and `linehits.tc` — [CT src/db-backend/src/omniscient_db.rs](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/src/db-backend/src/omniscient_db.rs)
- **Copy/avoid evidence from their own changelog.** The worker socket used to carry `Lang` as a `serde_repr` integer, which "made the declaration order of two independently-maintained enums … a binary contract". The two enums diverged, so on a skewed pair "a session starts and navigates normally and only the variables fail to load". They moved to string names, deliberately not backward compatible (26.10.1) — [CT CHANGELOG.md](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/CHANGELOG.md) (lines ~122–148)
- Also from their docs: jump commands deserialise into `task::Location` and navigate only by `rrTicks` (`location_jump` is `self.jump_to(StepId(location.rr_ticks.0))`). Because `Location` has a container-level `#[serde(default)]`, a payload written against the wrong struct deserialised to a zeroed location — [CT ct-dap.md](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/ct-dap.md)

#### CodeTracer trace format crates (MIT)
- The workspace members are `codetracer_trace_types`, `codetracer_trace_format_capnp`, `codetracer_trace_format_cbor_zstd`, `codetracer_trace_reader`, `codetracer_trace_writer`, `_writer_ffi`, `_writer_nim`, `codetracer_trace_util`, `trace_formatter`, `codetracer_ctfs`, `codetracer_trace_filter`, `origin_patterns`, `origin_pattern_discovery`, `sourcemap-translate`, `ct-mapping-tools` and `mapping-catalog`, at workspace version 0.19.0 — [RT Cargo.toml](https://github.com/metacraft-labs/runtime_tracing/blob/1f322ca8764a32788226707fb6218d2fc4c5f095/Cargo.toml)
- The event stream `TraceLowLevelEvent` has `Step(StepRecord{path_id,line})`, interning events (`Path`, `VariableName`, `Type`, `Function`), `Value(FullValueRecord)`, `Call`, `Return`, `Event`, `Asm`, history events (`BindVariable`, `Assignment`, `DropVariables`), experimental cell/compound events, `ThreadStart/ThreadExit/ThreadSwitch` and `DropLastStep` (because "the trace needs to be append-only") — [RT codetracer_trace_types/src/types.rs](https://github.com/metacraft-labs/runtime_tracing/blob/1f322ca8764a32788226707fb6218d2fc4c5f095/codetracer_trace_types/src/types.rs)
- The value model `ValueRecord` (tagged by `kind`) has `Int, Float, Bool, String, Sequence{elements,is_slice}, Tuple, Struct{field_values}, Variant{discriminator,contents}, Reference{dereferenced,address,mutable}, Raw, Error{msg}, None, Cell{place}, BigInt, Char`, each with a `type_id`. `TypeRecord{kind, lang_type, specific_info: None|Struct{fields}|Pointer}`. The value is fully materialized and nested; laziness is expressed only through `Cell{place}` — [RT types.rs](https://github.com/metacraft-labs/runtime_tracing/blob/1f322ca8764a32788226707fb6218d2fc4c5f095/codetracer_trace_types/src/types.rs)
- The CTFS container has magic `C0 DE 72 AC E2` and versions 2, 3 and 4. Byte 6 is the compression method (`None/Zstd/Lz4`) and byte 7 the encryption method (`None/Aes256Gcm`) — [RT codetracer_ctfs/src/header.rs](https://github.com/metacraft-labs/runtime_tracing/blob/1f322ca8764a32788226707fb6218d2fc4c5f095/codetracer_ctfs/src/header.rs)
- Chunked event streams are "independently-compressed chunks" with a 16-byte header `compressed_size: u32, event_count: u32, first_geid: u64` (zstd level 3 by default). A reader can seek to a GEID by chunk without decompressing earlier chunks — [RT codetracer_ctfs/src/chunked.rs](https://github.com/metacraft-labs/runtime_tracing/blob/1f322ca8764a32788226707fb6218d2fc4c5f095/codetracer_ctfs/src/chunked.rs)
- `mmap.bin` is a table of fixed 33-byte entries (address, size, binary_ref, file_offset, permissions) "for O(1) indexing" — [RT codetracer_ctfs/src/mmap_info.rs](https://github.com/metacraft-labs/runtime_tracing/blob/1f322ca8764a32788226707fb6218d2fc4c5f095/codetracer_ctfs/src/mmap_info.rs)

#### midas (VS Code extension, MIT)
- midas is a JavaScript VS Code extension with three backends: "midas-native (mdb, future hopefully mdb+rr), midas-gdb (gdb) and midas-rr (gdb+rr)". The old GDB/MI implementation was removed and "The exclusively supported variant is midas DAP implementation" (0.24.N) — [MI CHANGELOG.md](https://github.com/farre/midas/blob/25ebbe0538215f132d0d6db9dbfe9665e8b9926e/CHANGELOG.md). The README still describes it as using "the GDB/MI interface", which is out of date given that changelog — [MI README.md](https://github.com/farre/midas/blob/25ebbe0538215f132d0d6db9dbfe9665e8b9926e/README.md)
- **The architecture is DAP implemented in Python inside gdb.** `GdbProcess.spawnArgs` starts gdb with `-q -ex "source …/dap-wrapper/variables_reference.py" -ex "source …/dap-wrapper/dap.py"`, and the JS side talks to it over two Unix sockets, `/tmp/midas-commands` and `/tmp/midas-events` — [MI modules/dap/gdb.js](https://github.com/farre/midas/blob/25ebbe0538215f132d0d6db9dbfe9665e8b9926e/modules/dap/gdb.js)
- **The rr link is plain gdbserver.** The provider picks a free port and sets `target = {type:"extended-remote", parameter:"127.0.0.1:<port>"}`. It runs `rr replay -h <addr> -s <port> -p <pid> -k <trace>`, or `-f <pid>` for fork-without-exec processes, in a terminal — [MI modules/providers/midas-rr.js](https://github.com/farre/midas/blob/25ebbe0538215f132d0d6db9dbfe9665e8b9926e/modules/providers/midas-rr.js) (lines ~60–208)
- **Multi-process means picking one process before replay.** midas parses `rr ps <trace>` into `{pid, ppid, exit, cmd, noexec}` and walks back to find the binary for "forked without exec" rows; the user picks one process per session — [MI modules/utils/rrutils.js](https://github.com/farre/midas/blob/25ebbe0538215f132d0d6db9dbfe9665e8b9926e/modules/utils/rrutils.js)
- **Reverse execution and checkpoints** are Python DAP handlers that call gdb commands. `reverseContinue` runs `gdb.execute("reverse-continue")`. `stepBack` maps granularity to `reverse-stepi`/`reverse-step`/`reverse-next`. Custom requests: `reverse-finish`, `set-checkpoint` (`checkpoint`), `restart-checkpoint` (`run <id>`) and `delete-checkpoint`. Checkpoints come from parsing `info checkpoints` text (`id\twhen\twhere`), and `run-to-event` runs `gdb.execute(f"run {event}")` — [MI modules/python/dap-wrapper/dap.py](https://github.com/farre/midas/blob/25ebbe0538215f132d0d6db9dbfe9665e8b9926e/modules/python/dap-wrapper/dap.py) (lines 384–821, 987–1002)
- The checkpoint UI is a VS Code webview (`CheckpointsViewProvider`) with messages `add-checkpoint`, `update-checkpoints`, `name-checkpoint`, `run-to-checkpoint` and `goto-source-location` — [MI modules/ui/checkpoints/checkpoints.js](https://github.com/farre/midas/blob/25ebbe0538215f132d0d6db9dbfe9665e8b9926e/modules/ui/checkpoints/checkpoints.js); [MI modules/ui/checkpoints/ui_protocol.js](https://github.com/farre/midas/blob/25ebbe0538215f132d0d6db9dbfe9665e8b9926e/modules/ui/checkpoints/ui_protocol.js)
- Values come from gdb.Value plus gdb pretty-printers. Variable references are a dict that is cleared on every `gdb.events.cont`, so references are only valid at one stop — [MI modules/python/dap-wrapper/variables_reference.py](https://github.com/farre/midas/blob/25ebbe0538215f132d0d6db9dbfe9665e8b9926e/modules/python/dap-wrapper/variables_reference.py)
- midas-native uses the authors' own alpha debugger, `mdb` (github.com/theIDinside/mdebug), which "won't be provided here" — [MI README.md "Midas Native"](https://github.com/farre/midas/blob/25ebbe0538215f132d0d6db9dbfe9665e8b9926e/README.md)

#### rr MCP servers (Python, MIT/Apache-2.0)
- **rr-mcp** (jnjaeschke) defines 48 `Tool(...)` entries: `traces_list, trace_info, trace_processes, session_create, session_list, session_close, continue, reverse_continue, step, reverse_step, next, reverse_next, finish, reverse_finish, stepi, reverse_stepi, nexti, reverse_nexti, run_to_event, breakpoint_set/delete/list/enable/disable, watchpoint_set, backtrace, print, locals, args, frame_select, registers, examine_memory, when, threads_list, thread_select, checkpoint_create/restore/delete/list, source_list, source_path, source_files, interrupt, catch, handle_signal, find_in_memory, info, gdb_raw`. Live session state is exposed as MCP resources `rr://sessions/{id}` — [RRM src/rr_mcp/server.py](https://github.com/jnjaeschke/rr-mcp/blob/b10c323042ece18439fce48a1803318f85174b4d/src/rr_mcp/server.py); [RRM README.md](https://github.com/jnjaeschke/rr-mcp/blob/b10c323042ece18439fce48a1803318f85174b4d/README.md)

### Inferences
- What to copy from CodeTracer: (1) one `ReplaySession`-style trait with interchangeable backends (materialized DB vs live replay); (2) the seekable chunk header with a `first_geid`; (3) the tick-interval coverage cache (see the navigation section); (4) the origin-chain algorithm over watchpoint plus reverse-continue, including its stack-slot-reuse and cross-thread guards. What to avoid: a fat, stringly DAP-plus-events protocol (around 55 `ct/*` commands that answer through side-channel events); a second process boundary whose wire format depends on enum ordinals; and `serde(default)` on navigation payloads.
- The MCP servers all hold one gdb per replayed process and pass gdb's text through. None exposes time as a first-class value: `when` returns rr's event number as text. hopper's agent surface should expose typed `Moment`s and omniscient queries, not 48 gdb verbs.
- BugStalker's `ValueParser` plus specialisations is the most valuable reusable code for Rust types, but only after a refactor: make every `read_memory_by_pid` call go through a `trait MemoryReader { fn read(&self, addr, len) }` (RAD's space-read idea). MIT permits vendoring or forking it.
- For C/C++/Rust layouts, hopper should keep a data-driven layout table (regex on the type name, field-path rules, rustc-version ranges), modelled on Rust's `gdb_providers.py`/`lldb_providers.py` (MIT/Apache) and BugStalker's `version_switch!`, not hard-coded Rust.

### Gaps
- The source of CodeTracer's rr backend (`codetracer-native-backend`, `ct-native-replay`) is not public. How it drives rr (gdb, its own RSP client, or linked librr) and how it implements `MaterializeInterval` could not be read. All claims about it rest on the db-backend side of the socket.
- midas's `mdb` (theIDinside/mdebug) and its planned "mdb+rr" were not read.
- The Python body of rr-mcp's `gdbmi.py` (1,443 lines) was not read line by line; only the tool list and the session spawn code were.
- The RAD Debugger's `.c` files, the `rdi` format and its `eval.mdesk` tables were not read beyond the headers cited.

## What is the cleanest boundary between engine and GUI, and what hurt each project?

### Takeaway
Every project chose a process boundary speaking DAP or something DAP-shaped: CodeTracer (DAP superset over stdio, socket or
wasm worker), midas (DAP from JS into Python inside gdb over Unix sockets) and BugStalker (DAP server). The MCP servers
use MCP over gdb/MI. The documented pain is version skew across the boundary and payloads that are not self-describing.
For hopper, an in-process Rust library with a typed async API, plus thin DAP and MCP adapters on top of it, avoids both
problems for its own native GUI.

### Inferences
- The recommended boundary for hopper: a `hopper-engine` library crate with a typed async API (owned request/response enums, `Moment`, `ValueHandle`). The native GUI links it in process, on a worker thread or runtime, never the UI thread. DAP (`hopper-dap`) and MCP (`hopper-mcp`) are adapters that translate onto the same API, so the engine has one source of truth. If a process boundary is later needed (remote recordings, crash isolation from gdb), serialise the same Rust enums with string tags and a protocol version in the handshake, and never ordinals. This sidesteps CodeTracer's skew problem.
- Don't make DAP the core protocol: its value model (`variablesReference` integers valid only while stopped, as midas's clearing shows) has no notion of "a value at another time".

### Gaps
- No measured cost (latency, serialisation) of CodeTracer's DAP-over-stdio for large payloads was found in the files read.

## How do they represent "a moment in time" and "a value at a moment"?

### Takeaway
CodeTracer uses three coordinates side by side: `StepId` for materialized traces, a global event id (`geid`) for CTFS
streams and replay restore, and rr ticks (`rrTicks`, with `tid`) for native replay. `RestoreAt{geid, tid, tick, phase}`
is its fullest "moment". The gdb-based tools have no moment type at all: they use rr's `when` event number or gdb
checkpoint ids. Values are either fully materialized trees (CodeTracer `ValueRecord`) or live gdb/ptrace reads valid
only at the current stop (midas, BugStalker).

- rr-mcp and karellen expose `when`/`rr_when` as a tool — [RRM server.py](https://github.com/jnjaeschke/rr-mcp/blob/b10c323042ece18439fce48a1803318f85174b4d/src/rr_mcp/server.py); [KRM server.py](https://github.com/karellen/karellen-rr-mcp/blob/2cca210258cb5dfe886f94edb0401bae4c56c8b3/src/main/python/karellen_rr_mcp/server.py) (line 244)
- RAD keys every evaluation by an `E_Space` (for example a process id) and a space generation from `E_SpaceGenFunction` — [RAD eval_core.h](https://github.com/EpicGamesExt/raddebugger/blob/e34454ff7a2ad92cd57925412d1e405b93babc5c/src/eval/eval_core.h)

### Inferences
- hopper's `Moment` should be one totally ordered, serialisable value: `Moment { recording: RecordingId, frame_time: u64 /* rr event (FrameTime) */, tid: Tid, ticks: u64 /* rr per-task ticks within that event */, sub: u32 /* singlestep index for an instruction-exact moment */ }`. Its order is (frame_time, ticks, sub) within the trace's single global order. rr serialises execution on one core, so a global order exists. Keep `StepId` only as an index into hopper's own materialized tables, never as a stand-in for ticks (CodeTracer's overloading is a lesson).
- A "value at a moment" should be `(Moment, Place)`, where `Place` is an address range in an address space (process plus vm generation) or a register in a frame. A RAD-style space-read hook keyed by `(process, Moment)` makes the evaluator time-agnostic: a read is answered from the materialized write index when covered, and otherwise by seeking rr to the moment.
- A value handle must not be a DAP integer that dies on continue. It should be `(Moment, ExprId or Place, type key, path)`, so the GUI can re-ask at another moment ("show this expression's history").

### Gaps
- How `ct-native-replay` maps a `geid` to an rr position internally is not visible in the public tree.

## How do they make navigation fast (caches, precomputed call trees, background indexing)?

### Takeaway
CodeTracer has the only real speed machinery: chunk-seekable compressed streams, lazily expanded call trees, separate
replay workers for UI stepping versus background flow and tracepoint work, and a coverage-aware materialization cache
that re-executes a tick interval only once and writes the result back into the trace file. The gdb wrappers rely on
rr's checkpoints and gdb's speed. BugStalker's DWARF tricks (parallel unit loading, lazy unit parts) apply to hopper's
symbol layer.

### Cited Findings
- The materialization cache works in steps: "Check `coverage.tc` … If it is recorded COVERED, serve from the materialized maps — no re-execution". On a miss, "the Memory Recreator … re-executes that interval and materializes its writes", appends them to an `IntervalTaggedMap` (address mapped to per-interval, tick-sorted write lists, and `global_line_index` mapped to line-hit lists), writes the interval "back into the `.ct` through the M2 copy-on-write overlay" (`Persist` or `InMemory` mode) and records it in `coverage.tc`. "Subsequent visits are hits … after a warm restart" — [CT src/db-backend/src/ctfs_trace_reader/materialization_cache.rs](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/src/db-backend/src/ctfs_trace_reader/materialization_cache.rs) (module doc and lines 79–160, 263–335, 480)
- Three task threads, "stable", "flow" and "tracepoint", each get their own request channel and `task_thread`. `run_to_entry` is true only for "stable" — [CT dap_server.rs](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/src/db-backend/src/dap_server.rs) (lines ~3544–3620). Replay workers are created with `--name`/`--index` — [CT recreator_session.rs](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/src/db-backend/src/recreator_session.rs)

- BugStalker: rayon-parallel compilation-unit parsing plus a lazy `OnceCell` part per unit — [BS dwarf/loader.rs](https://github.com/godzie44/BugStalker/blob/6817f52b48a890d5d0ee3b78155bed1357fceb5b/src/debugger/debugee/dwarf/loader.rs); [BS dwarf/unit/mod.rs](https://github.com/godzie44/BugStalker/blob/6817f52b48a890d5d0ee3b78155bed1357fceb5b/src/debugger/debugee/dwarf/unit/mod.rs)

### Inferences
- Copy for hopper: (1) a pool of rr replay replicas, one "cursor" replica for the user and N background replicas for indexing and queries, so background work never moves the user's position; (2) an interval-coverage table keyed by `Moment` ranges, so any expensive re-execution is done once and persisted next to the rr trace (not inside it; rr's trace directory should stay untouched); (3) a call tree built by a background pass and paged to the GUI by row range; (4) a per-line hit index (line to sorted moments) for "every execution of this line".
- Avoid: CodeTracer's flow preloader drives the user-facing replay with breakpoint, continue and step loops. Anything the GUI shows passively (flow values, history) should come from background replicas or the index.

### Gaps
- No timings for CodeTracer's rr path appeared in the files read; their bench doc (cited in the earlier research) still marks most cells `PENDING`.

## How do they handle multi-threaded and multi-process recordings?

### Takeaway
Multi-process support everywhere is "choose one process per session": `rr replay -p/-f`, one gdb each. CodeTracer adds a
multi-trace session layer that multiplexes per-trace handlers behind composed thread ids, plus cross-thread and
cross-process origin hops. Threads within a process are handled through gdb's or rr's thread selection; CodeTracer's
DAP `threads` is documented as a "single-threaded model".

### Cited Findings

- rr-mcp: "Concurrent replay sessions for debugging different processes simultaneously … exec'd processes (`pid`) or forked-without-exec children (`fork_pid`)". With `-f`, "rr replays the trace forward until the" fork before starting — [RRM README.md](https://github.com/jnjaeschke/rr-mcp/blob/b10c323042ece18439fce48a1803318f85174b4d/README.md); [RRM session.py](https://github.com/jnjaeschke/rr-mcp/blob/b10c323042ece18439fce48a1803318f85174b4d/src/rr_mcp/session.py) (lines 93–141)

## Proposed crate layout and API surface for hopper v1

### Takeaway
A Cargo workspace whose engine is a library, not a server. rr is driven over its gdbserver RSP with hopper's own Rust
client (no gdb process in the value path). DWARF evaluation is native, on gimli plus a BugStalker-derived value model
behind a time-aware memory trait. The index is built in the background by replica replays. DAP and MCP are thin adapters.
Everything below is a design proposal (inference) built from the findings above, not something any studied project ships.

### Cited Findings
- Grounding for the choices: the replica threads ("stable"/"flow"/"tracepoint") — [CT dap_server.rs](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/src/db-backend/src/dap_server.rs); the coverage cache — [CT materialization_cache.rs](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/src/db-backend/src/ctfs_trace_reader/materialization_cache.rs); the watchpoint/reverse-continue origin loop — [CT recreator_origin.rs](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/src/db-backend/src/recreator_origin.rs); space-read hooks — [RAD eval_core.h](https://github.com/EpicGamesExt/raddebugger/blob/e34454ff7a2ad92cd57925412d1e405b93babc5c/src/eval/eval_core.h); the Rust layouts — [RUST gdb_providers.py](https://github.com/rust-lang/rust/blob/3b5aab2cea0711a2cc87a5a71338b5dba241b6a9/src/etc/gdb_providers.py), [BS specialization/mod.rs](https://github.com/godzie44/BugStalker/blob/6817f52b48a890d5d0ee3b78155bed1357fceb5b/src/debugger/variable/value/specialization/mod.rs); and the agent tool surfaces that exist today — [RRM server.py](https://github.com/jnjaeschke/rr-mcp/blob/b10c323042ece18439fce48a1803318f85174b4d/src/rr_mcp/server.py)

### Inferences
Proposed workspace (each crate a dependency boundary):

| Crate | Role | Depends on |
|---|---|---|
| `hopper-core` | Vocabulary: `RecordingId`, `Moment{frame_time, tid, ticks, sub}`, `MomentRange`, `ProcessId` (rr task group plus exec generation), `ThreadId`, `Place` (memory range in a space, or a register in a frame), `SourceLoc`, `FnId`, the typed error and refusal enum. No I/O. | none |

| `hopper-rr` | rr process management: `rr record`, `rr ps` (process table), `rr replay -s <port> -p/-f <pid>` per replica, checkpoint bookkeeping, `seek(Moment)` = nearest checkpoint, then run forward with ticks targets; the `ReplicaPool` (one cursor replica plus N background replicas; a lease API). | `hopper-symbols` | ELF/DWARF loading on gimli/object/addr2line: rayon-parallel compilation units, lazy unit parts, PC to line, PC to function and scopes, variable location lists, `.eh_frame` unwinding. | `hopper-eval` | DWARF expression evaluator plus expression language (parse to IR to interpreter) over a `trait Space { fn read(&self, place, out) -> Result<Coverage>; fn generation(&self) -> u64 }` (RAD). | `hopper-engine` | The one public API (below); owns the replica pool, index jobs, caches and the `Space` impl that answers reads from the index when covered and from a replica otherwise. Async (tokio or a small executor) and never on the UI thread. | all above |
| `hopper-dap` | DAP adapter: standard requests plus `stepBack`/`reverseContinue`; omniscient queries as `hopper/*` requests that return their payload *in the response* (not side events), with typed, string-tagged JSON and a protocol version. | engine |

Proposed `hopper-engine` API for v1 (async, owned types; every result carries the `Moment` it answers for):
- Session: `Engine::open(trace_dir) -> Session`; `Session::processes() -> Vec<ProcessInfo>`; `threads(ProcessId, Moment)`; `timeline() -> Timeline { start, end, events: syscalls, signals, execs, thread start/exit }`; `index_status() -> IndexProgress` (stream).
- Cursor (the user's position, on the cursor replica): `cursor() -> Cursor{moment, thread, frame}`; `step(StepKind{Into|Over|Out|Instruction}, Direction{Forward|Backward}) -> Stop`; `run(Direction, until: Until{Breakpoint(set)|Watch(Place)|Moment|Signal|EndOfTrace}) -> Stop`; `seek(Moment) -> Stop`; `back()/forward()` history (rr's `rr-history-push`/`back`/`forward` idea).
- Values: `frames(Moment, ThreadId) -> Vec<Frame>`; `scopes(Moment, FrameId) -> Vec<Scope>`; `eval(Moment, FrameId, expr) -> ValueHandle`; `children(ValueHandle, range) -> Vec<ValueHandle>` (paged, RAD block ranges); `read_memory(ProcessId, Moment, addr, len) -> Bytes`.
- Omniscient (index-backed, with a `Coverage` flag saying "complete", or "partial: these ranges pending"): `calls(ProcessId, filter, range) -> Page<CallNode>`; `line_hits(SourceLoc, MomentRange) -> Page<Moment>`; `value_history(expr or Place, MomentRange) -> Page<(Moment, ValueHandle)>`; `last_write(Place, before: Moment) -> Option<WriteEvent{moment, pc, thread}>`; `origin(ValueHandle, budget) -> OriginChain` (CodeTracer's algorithm with its guards).
- `ValueHandle` = `(Moment, ProcessId, FrameId?, ExprId or Place, TypeKey, path)`. It never expires, and the GUI can re-evaluate it at another `Moment`.
- The MCP tool set: `recording_info`, `processes`, `seek`, `step`, `run_until`, `stack`, `eval`, `memory`, `calls`, `line_hits`, `value_history`, `last_write`, `origin`. Each returns JSON with explicit `moment` fields, and `when` is not needed as a separate tool.

What hopper v1 should defer: a gdb process in the value path (use it only as a debugging console bridge), multi-trace sessions, and a remote process boundary (keep the same enums serialisable so it can be added later).

### Gaps
- Whether an RSP client alone can provide everything hopper needs from rr without gdb (for example `qXfer:libraries-svr4` and TLS lookup, which rr's gdbserver may not implement) was not verified in rr's source in this pass.
- No measurement exists yet of how fast replica-based indexing (singlestep or breakpoint-driven) runs on real recordings; the index design above is unmeasured.

# Teach rr's dataflow to speak Rust ownership

**Yes: Rust's ownership facts can turn machine-level "this byte came from that `memcpy`" answers into source-level "`b` was moved from `a` at line 11, then cloned into `c`" answers, and the join is mechanical rather than heuristic.** rustc's MIR is the only place where moves, copies, borrows, projections, storage markers and drops are explicit events, and none of them survive into DWARF ([rustc dev guide, MIR](https://rustc-dev-guide.rust-lang.org/mir/index.html); [notes rust-static-provenance.md:71](#n-rsp)). hopper therefore needs a **sidecar**: a table of ownership events emitted from the final optimised MIR, in the same rustc invocation that builds the recorded binary, keyed by (instance symbol, span, inline chain, statement order) and joined to program counters through DWARF line tables ([notes rust-static-provenance.md:139](#n-rsp)). The machine side stays Pernosco's model, which follows copies backward through memory and registers and stops at arithmetic, I/O or immediates ([O'Callahan 2019](https://robert.ocallahan.org/2019/11/explaining-dataflow-in-pernosco.html)); the sidecar relabels and collapses those machine hops. No prior debugger was found that labels a dynamic machine slice with static Rust ownership facts, so this is hopper's most distinctive idea, and also an unproven one ([notes rust-static-provenance.md:111](#n-rsp)). The first implementation is a Rust workspace whose engine is a library, driving `rr replay -s` through hopper's own RSP client, evaluating DWARF natively over a time-aware memory trait, and serving a skelter GUI, a CLI, MCP and DAP from one typed API ([notes existing-frontends.md:255-288](#n-ef)). The plan starts with a thin vertical slice (record, replay over RSP, source plus locals at a moment, reverse step), then adds a cheap breakpoint-only index, machine provenance, the ownership sidecar, and only then the per-instruction omniscient index. Two facts gate everything: rr cannot record or replay in the cloud containers this work usually runs in, because they have no hardware PMU ([notes rr-internals.md:213-226](#n-rr)), and the sidecar ties the recorded binary to one pinned nightly toolchain ([notes rust-static-provenance.md:60](#n-rsp)).

## Ownership facts live only in MIR, so hopper must carry them in a sidecar

The vocabulary hopper wants already exists inside rustc. A MIR place is "an expression like `_3`, `_3.f` or `*_3`", with field, deref, index and downcast projections; an operand is explicitly `copy` or `move`; borrows are `&`/`&mut` rvalues; `StorageLive`/`StorageDead` bracket a local's life; `debug name => place` annotations tie user variable names to places; and every statement carries a span and source scope ([rustc dev guide, MIR](https://rustc-dev-guide.rust-lang.org/mir/index.html)). Each `SourceScopeData` records MIR inlining as `inlined: Option<(Instance, Span)>`, the callee and the call site ([rustc_middle docs](https://doc.rust-lang.org/nightly/nightly-rustc/rustc_middle/mir/struct.SourceScopeData.html)). DWARF keeps none of the event kinds. It keeps spans as line rows and inlined-subroutine trees, plus variable locations, so **a moved-from `String` stays in scope with a valid-looking location and stale bytes**, and a debugger shows it as live ([notes rust-static-provenance.md:82](#n-rsp)). No 2025H2 Rust project goal targets ownership debuginfo ([Project goals 2025H2](https://blog.rust-lang.org/2025/10/28/project-goals-2025h2)), so waiting for upstream is not an option.

The join key is therefore not a MIR statement id, which codegen never emits, but **(instance symbol, span, inline scope chain)**, the only key that survives into DWARF ([notes rust-static-provenance.md:29](#n-rsp)). Several MIR statements often share one span (`let b = a;` yields a move and storage markers on the same span), so the sidecar keeps an ordered list of events per span and hopper picks among them by matching the observed machine effect: which bytes were read from which variable's DWARF location and written to which ([notes rust-static-provenance.md:29, 155](#n-rsp)). The rows must come from the *final optimised, monomorphised* MIR that codegen lowers, not borrowck MIR, or their places will not match DWARF variables ([notes rust-static-provenance.md:31](#n-rsp)). At `-O0` a move is typically a whole-place copy inside the statement's PC range between stable stack slots, which makes labels exact; in release builds a move often produces no machine copy at all, and the honest answer becomes "same bytes, renamed from `a` to `b`", which only the sidecar can give ([notes rust-static-provenance.md:30-31](#n-rsp)). MIR passes such as DestinationPropagation and ref_prop rewrite locals and their debuginfo, and had remapping bugs as late as October 2025 ([rust-lang/rust PR #147525](https://github.com/rust-lang/rust/pull/147525)), so every label must carry a confidence grade.

Getting MIR out has one cost that shapes the whole project. Everything that reads MIR needs nightly plus `rustc-dev`. `rustc_public` (ex-Stable MIR) is still not on crates.io and has "no stable way to initialize the compiler yet" ([rustc_public book](https://rust-lang.github.io/rustc_public/print.html); [notes rust-static-provenance.md:46](#n-rsp)). The practical framework is `rustc_plugin`, whose v0.15 pins `nightly-2026-05-01` (rustc 1.96) and treats each nightly bump as a breaking change ([rustc_plugin README](https://github.com/cognitive-engineering-lab/rustc_plugin)). Because spans and MIR can differ between rustc versions, building the binary on stable and the sidecar on nightly breaks the join: **the recorded binary must be built by the pinned nightly, with the sidecar emitted from the same invocation** ([notes rust-static-provenance.md:60](#n-rsp)). Charon and `-Znll-facts` work on pre-optimisation MIR and are useful only as optional labels, and Flowistry's per-function dependency sets are hints for pruning, not ground truth, because they analyse calls by signature only and miss interior mutability ([Flowistry README](https://github.com/willcrichton/flowistry); [notes rust-static-provenance.md:58-59](#n-rsp)).

The sidecar pipeline, a design no tool ships today, is a `cargo hopper-build` wrapper on `rustc_plugin` that sets `RUSTC_WORKSPACE_WRAPPER` for every crate, passes `-C debuginfo=2 -C force-frame-pointers=yes -Z always-encode-mir`, disables incremental builds, walks the codegen'd instances after analysis, and writes per-instance rows of `{symbol, bb, stmt, span, inline chain, kind, src place, dst place, type, size}` where kind is one of move, copy, shared or mutable borrow, reborrow, raw address-of, projection, deref, drop, storage-live, storage-dead, call (with `Clone::clone`, `ToOwned` and `From` flagged), aggregate and discriminant write ([notes rust-static-provenance.md:151-155](#n-rsp)). A link step merges the per-crate files and stamps the binary's GNU build-id so a stale sidecar is rejected. The known failure modes are LLVM inlining after the sidecar is written (match by `DW_AT_abstract_origin` plus span), vanished or merged moves under optimisation (confidence grades and a raw fallback), shared generics (dedupe by v0 symbol), precompiled std (no sidecar unless `-Z build-std`), and unsafe code, FFI and `UnsafeCell`, where labels still describe what MIR did but ownership-based pruning must switch off ([notes rust-static-provenance.md:158-165](#n-rsp)).

## A worked example: what rr alone answers, and what the sidecar adds

Take a small program built at `-O0` with `cargo hopper-build`, recorded with `rr record`.

```rust
#[derive(Clone)]
struct Config { name: String, retries: u32 }

fn load() -> Config {
    let name = String::from("alpha");     // line 5
    Config { name, retries: 3 }           // line 6
}

fn main() {
    let a = load();                       // line 10
    let b = a;                            // line 11: move
    let c = b.clone();                    // line 12: clone (a call)
    let mut v = Vec::new();               // line 13
    v.push(c);                            // line 14: move into the Vec's heap buffer
    let n = &v[0].name;                   // line 15: index + field projection + borrow
    println!("{n}");                      // line 16
}
```

At line 16 the user clicks the text `alpha` that `n` points to and asks where it came from. **rr alone**, driven the way CodeTracer's origin loop drives it (seek, take the address, set a write watchpoint, reverse-continue, resolve the PC, repeat, with guards for stack-slot reuse and cross-thread writes) ([CodeTracer recreator_origin.rs](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/src/db-backend/src/recreator_origin.rs)), or Pernosco-style copy following, returns a chain of machine hops. The five heap bytes at the clone's buffer were last written by a `memcpy` inside the slice-to-`Vec` copy that `String::clone` calls; that `memcpy` read them from a different heap buffer; that buffer was written by a `memcpy` from `.rodata` inside `String::from`. Following the pointer instead (the `ptr` field of `v[0].name`) gives a write inside `Vec::push`'s `ptr::write` from a stack slot, an earlier write to that slot from `clone`'s return registers, and so on. Every hop is a PC in a std function and a raw address; the user's own variables appear only where a PC happens to fall on a user line. The chain is correct, and Pernosco notes that this copy-skipping is "especially useful for Rust", which moves data often ([Pernosco dataflow](https://pernos.co/about/dataflow/)), but it describes `memcpy`s, not the program.

**With the sidecar and a heap-lineage index**, hopper relabels each machine hop by looking up its PC's (symbol, line row, inline chain) and choosing the sidecar event whose source and destination places' DWARF locations match the bytes the instruction read and wrote ([notes rust-static-provenance.md:104-105, 155](#n-rsp)). It names heap addresses by allocation lineage, built from allocator breakpoints during replay ([notes dynamic-provenance.md:371-382](#n-dp)). The same click then reads as follows (illustrative; the exact hop count depends on codegen).

| Hop | rr alone (machine) | hopper with sidecar (source) | Confidence |
|---|---|---|---|
| 1 | load of pointer at stack slot S7 | `n = &v[0].name`: shared borrow of field `name` of element 0 of `v` (line 15) | exact |
| 2 | `memcpy` in `Vec::push` from S5 to heap H3+0 | `v[0]` ← **move** `c` into `v` (line 14); H3 is allocation #2, created by `RawVec` grow during this push | exact |
| 3 | bytes at H2 written by `memcpy` in `<[u8]>::to_vec`, reading H1 | `c` ← **`Clone::clone(&b)`** (line 12); `c.name`'s buffer is allocation #3, its bytes copied from `b.name`'s buffer (allocation #1) | exact (call flagged) |
| 4 | stack copy S3 → S4 | `b` ← **move** `a` (line 11). `a` is shown greyed as *moved-out* from here on, although DWARF still shows it as a valid `String` | exact at -O0; "inferred rename" if no copy exists |
| 5 | return-slot copy in `load` epilogue | `a` ← return value of `load()` (line 10), built by aggregate `Config { name, retries: 3 }` with `name` **moved** in (line 6) | exact |
| 6 | `memcpy` from `.rodata` in `String::from` | `name` ← `String::from("alpha")` (line 5): origin is a string literal. Chain ends at an immediate source | exact |

Three things in this table are unavailable to rr alone. The **move/clone distinction** tells the user that `c` owns separate bytes while `b` and `a` are the same bytes under new names, which is the ownership fact a reader of the code actually needs. The **moved-out state** of `a` fixes a misleading display, since DWARF gives no end to `a`'s validity ([notes rust-static-provenance.md:82-83](#n-rsp)). The **collapse of std internals** into one source hop per ownership event is Pernosco's "skip trivial copies" heuristic with compiler-given boundaries instead of guessed ones ([notes rust-static-provenance.md:104](#n-rsp)). A fourth benefit is a hypothesis to test: after a move, borrowck guarantees the source place is dead for reads, so a backward search for "who last wrote `b`'s bytes" can jump straight to `a`'s history at the move without scanning for aliased writers, except in unsafe code ([notes rust-static-provenance.md:107](#n-rsp)). Had `v` been dropped, the sidecar's drop events plus the allocator log would also say "allocation #2 freed by drop of `v` at line 17", and a niche-only write would read "variant changed to `None`" rather than a field store ([notes rust-static-provenance.md:84](#n-rsp)).

The click semantics stay layered, as the dynamic-provenance notes recommend: follow copy chains by default; at an arithmetic node show the operands and let the user pick one; show address dependencies such as `map[key]` but never follow them automatically, because pointer tainting is known to over-taint ([Slowinska & Bos, EuroSys 2009](https://talks.cam.ac.uk/talk/index/17038/); [notes dynamic-provenance.md:329-341](#n-dp)). For hopper's first heavy user, cadabra3's `f64` geometry, most interesting values are computed rather than copied, so the one-level arithmetic expansion and named semantic anchors such as cadabra3's `site!` decision events matter more than deep copy chains ([notes dynamic-provenance.md:342-343](#n-dp)). None of this needs forward taint. "Where did this come from" is a backward walk over a last-writer log plus each instruction's inputs, demand-driven as in lazy dynamic slicing ([Zhang, Gupta, ICSE 2003](https://www.cs.purdue.edu/homes/xyzhang/Comp/icse03.pdf); [notes dynamic-provenance.md:105-111](#n-dp)). Off-the-shelf taint engines do not fit: DFSan has 8 labels and Rust users could not get it to link as of April 2026, and Valgrind, Pin and DynamoRIO cannot instrument an rr replay ([users.rust-lang.org thread](https://users.rust-lang.org/t/how-to-use-dataflow-sanitizer/139842); [rr issue #16](https://github.com/rr-debugger/rr/issues/16)).

## The first implementation: a library engine over rr's gdbserver

### rr gives hopper a serial timeline and a small, sufficient packet set

rr's gdbserver speaks plain RSP plus reverse `bc`/`bs`, a `vRun` seek that takes an event number, `t<ticks>` or `c<checkpoint>`, and a `qRRCmd:<name>:<tid>` escape to `when`, `when-ticks`, `checkpoint` and the rest ([GdbServerConnection.cc#L1155-L1204](https://github.com/rr-debugger/rr/blob/ca20dcb/src/GdbServerConnection.cc#L1155-L1204); [DebuggerExtensionCommand.cc#L14-L227](https://github.com/rr-debugger/rr/blob/ca20dcb/src/DebuggerExtensionCommand.cc#L14-L227)). It runs exactly one thread at a time, targets one process per server, advertises no fork or exec events, and has **four x86 hardware watchpoint slots** before gdb would fall back to single-stepping ([GdbServer.cc#L1088-L1105](https://github.com/rr-debugger/rr/blob/ca20dcb/src/GdbServer.cc#L1088-L1105); [Task.cc#L1922-L1931](https://github.com/rr-debugger/rr/blob/ca20dcb/src/Task.cc#L1922-L1931)). Reverse continue is forward replay from an earlier checkpoint that remembers the last stop, capped at 20 repeated stops ([ReplayTimeline.cc#L943-L1010](https://github.com/rr-debugger/rr/blob/ca20dcb/src/ReplayTimeline.cc#L943-L1010)). Automatic checkpoints sit about 0.5 s of replay apart so a reverse operation within that window "should take at most a second" ([ReplayTimeline.cc#L1521-L1556](https://github.com/rr-debugger/rr/blob/ca20dcb/src/ReplayTimeline.cc#L1521-L1556)). `qRRCmd` replies are free text such as `"Current tid: "`, so hopper's client parses strings that can change between rr versions and must pin the rr version ([notes rr-internals.md:41, 80](#n-rr)). No maintained Rust RSP client exists, so hopper owns one (prior report:26).

The time model follows rr's. An rr time is an event number (global, totally ordered because threads are serialised) plus the current thread's tick count, a count of retired conditional branches that **resets at clone and exec**; rr itself says `(event, ticks, step key)` "do not uniquely identify a program state" and disambiguates by registers ([ReplayTimeline.h#L260-L300](https://github.com/rr-debugger/rr/blob/ca20dcb/src/ReplayTimeline.h#L260-L300); [GdbServer.cc#L1699-L1712](https://github.com/rr-debugger/rr/blob/ca20dcb/src/GdbServer.cc#L1699-L1712)). hopper's `Moment` is therefore `{recording, frame_time, tid, ticks, sub}`, where `sub` is the instruction ordinal since the last tick change, ordered by (frame_time, ticks, sub), stored with the trace uuid and the trace's `TRACE_VERSION` (85 today; compatibility is all-or-nothing) ([TraceStream.cc#L1648-L1659](https://github.com/rr-debugger/rr/blob/ca20dcb/src/TraceStream.cc#L1648-L1659); [notes rr-internals.md:108-110](#n-rr); [notes existing-frontends.md:176](#n-ef)). CodeTracer's overloading of rr ticks as a step id, and jump payloads that silently deserialised to a zeroed location, are the mistakes to avoid ([CodeTracer ct-dap.md](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/ct-dap.md)).

### Crate layout and the one engine API

Nothing studied is adoptable whole. CodeTracer's rr backend is a separate, licence-gated binary whose source is private, and its front end is AGPLv3; midas and the three rr MCP servers wrap gdb text; BugStalker has the best Rust value model but reads memory through `ptrace` directly ([notes existing-frontends.md:37-45](#n-ef); [CodeTracer recreator_session.rs](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/src/db-backend/src/recreator_session.rs)). Every project that put a process boundary at the centre paid for it in version skew; CodeTracer's worker socket made two enums' declaration order "a binary contract", and a skewed pair would navigate normally while "only the variables fail to load" ([CodeTracer CHANGELOG.md](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/CHANGELOG.md)). hopper's engine is a library linked in process by the GUI, with DAP and MCP as adapters over the same typed API.

| Crate | Owns | Depends on |
|---|---|---|
| `hopper-core` | `RecordingId`, `Moment`, `MomentRange`, `ProcessId` (rr task group plus exec generation), `ThreadId`, `Place` (memory range in a space, or a register in a frame), `SourceLoc`, typed errors. No I/O | none |
| `hopper-rsp` | RSP client: framing, no-ack, `vCont`, `bc`/`bs`, `Z0`–`Z4`, `m`/`g`/`p`, `qXfer`, `vRun` seeks, `qRRCmd`; tested against recorded packet transcripts | core |
| `hopper-rr` | `rr record`, `rr ps`, `rr traceinfo`, one `rr replay -s 0 -p <pid>` per replica, checkpoint bookkeeping, `ReplicaPool` (one cursor replica, N background replicas, leases) | core, rsp |
| `hopper-symbols` | ELF/DWARF on `object`/`gimli`/`addr2line`: parallel CU loading, lazy unit parts, PC→line/function/inline chain, location lists, CFI unwinding; on-disk symbol cache | core |
| `hopper-eval` | DWARF expression evaluator and expression language over a `Space` trait; lazy `ValueTree`; data-driven Rust std layout table | core, symbols |
| `hopper-sidecar` | the `.hsc` reader, build-id check, PC→ownership-event join and disambiguation | core, symbols |
| `hopper-build` | `cargo hopper-build` CLI plus the `rustc_plugin` driver that writes `.hsc` files; pinned nightly; builds separately from the rest | rustc_plugin |

| `hopper-engine` | the public API; owns replicas, index jobs, caches and the `Space` impl | all above |
| `hopper-dap`, `hopper-mcp`, `hopper-cli`, `hopper-gui` | adapters and front ends | engine |

This is the notes' proposed layout ([notes existing-frontends.md:265-280](#n-ef)) with the sidecar split out, because the driver must compile against `rustc-dev` on a pinned nightly while the rest of hopper should build on the ordinary toolchain. The engine API, in outline:

```rust
pub struct Moment { pub recording: RecordingId, pub frame_time: u64, pub tid: Tid, pub ticks: u64, pub sub: u32 }
pub struct ValueHandle { pub at: Moment, pub process: ProcessId, pub frame: Option<FrameId>,
                         pub target: ExprOrPlace, pub ty: TypeKey, pub path: FieldPath } // never expires

impl Session {
    fn processes(&self) -> Vec<ProcessInfo>;
    fn timeline(&self) -> Timeline;                       // syscalls, signals, execs, thread start/exit
    fn index_status(&self) -> Receiver<IndexProgress>;
    // cursor, on the cursor replica
    fn step(&self, kind: StepKind, dir: Direction) -> Result<Stop>;
    fn run(&self, dir: Direction, until: Until) -> Result<Stop>;   // Breakpoints | Watch(Place) | Moment | EndOfTrace
    fn seek(&self, to: Moment) -> Result<Stop>;
    fn back(&self) -> Option<Stop>; fn forward(&self) -> Option<Stop>; // navigation undo/redo
    // values at any moment
    fn frames(&self, at: Moment, t: ThreadId) -> Result<Vec<Frame>>;
    fn eval(&self, at: Moment, f: FrameId, expr: &str) -> Result<ValueHandle>;
    fn children(&self, v: &ValueHandle, rows: Range<u64>) -> Result<Vec<ValueHandle>>;
    fn ownership(&self, v: &ValueHandle) -> Result<OwnershipState>;  // Live | MovedOut{to, at} | Dropped{at} | Unknown
    // omniscient: every result says Complete or Partial{pending ranges}
    fn calls(&self, p: ProcessId, f: CallFilter, page: PageReq) -> Result<Page<CallNode>>;
    fn line_hits(&self, loc: SourceLoc, r: MomentRange) -> Result<Page<Moment>>;
    fn value_history(&self, v: &ValueHandle, r: MomentRange) -> Result<Page<(Moment, ValueHandle)>>;
    fn last_write(&self, place: Place, before: Moment) -> Result<Option<WriteEvent>>;
    fn origin(&self, v: &ValueHandle, budget: Budget) -> Result<OriginChain>; // hops carry machine + ownership labels
}
```

The value handle is the important departure from DAP, whose `variablesReference` integers die at the next continue (midas clears them on every `cont` event), so they cannot express "this expression at another time" ([midas variables_reference.py](https://github.com/farre/midas/blob/25ebbe0538215f132d0d6db9dbfe9665e8b9926e/modules/python/dap-wrapper/variables_reference.py); [notes existing-frontends.md:149-150, 178](#n-ef)). Each `OriginChain` hop carries both layers, `{moment, pc, read: Place, written: Place, machine_kind, ownership: Option<{kind, src, dst, span, confidence}>}`, so the GUI can show the source view by default and the machine view on demand. Concurrency follows cadatomic's job pattern: std threads, results drained once per frame, cancellation, and a real idle barrier for tests ([cadatomic jobs.rs:1-10](file:///home/user/cadatomic/crates/cadatomic-core/src/jobs.rs)). Because each rr replica is inherently serial, a blocking RSP client on one worker thread per replica, fed by a request channel, is simpler than an async runtime (an inference; nothing measured favours either).

### Value evaluation reuses BugStalker's model behind a time-aware read hook

The evaluator is the largest real work item (prior report:54). RAD Debugger's design shows the abstraction: every read goes through a pluggable space-read function, and a space generation counter invalidates caches ([RAD eval_core.h](https://github.com/EpicGamesExt/raddebugger/blob/e34454ff7a2ad92cd57925412d1e405b93babc5c/src/eval/eval_core.h)). hopper's `Space` is keyed by `(process, Moment)` and answers a read from the write index when that interval is covered and from a replica seek otherwise ([notes existing-frontends.md:177](#n-ef)). BugStalker (MIT) supplies the rest after one refactor: its gimli evaluation loop, its `ValueParser` over a type graph, its specialisations for `Vec`, `String`, `HashMap`, `BTreeMap`, `Rc`, `Arc`, `RefCell` and others, and its `version_switch!` for rustc-version layouts (thread-locals differ across 1.89 and 1.94; `VecDeque::head` changes in 1.97), with every `read_memory_by_pid` replaced by `Space::read` ([BugStalker specialization/mod.rs](https://github.com/godzie44/BugStalker/blob/6817f52b48a890d5d0ee3b78155bed1357fceb5b/src/debugger/variable/value/specialization/mod.rs); [BugStalker mod.rs#L1312](https://github.com/godzie44/BugStalker/blob/6817f52b48a890d5d0ee3b78155bed1357fceb5b/src/debugger/mod.rs)). Std layouts should live in a data table seeded from Rust's own `gdb_providers.py` (for example `Vec` data at `buf.inner.ptr`, hashbrown slots occupied when `ctrl[i] & 128 == 0` with elements stored before ctrl) rather than hard-coded ([Rust gdb_providers.py](https://github.com/rust-lang/rust/blob/3b5aab2cea0711a2cc87a5a71338b5dba241b6a9/src/etc/gdb_providers.py)). Rust enums use rustc's `variant_part` and niche discriminants ([rustc enums debuginfo](https://doc.rust-lang.org/nightly/nightly-rustc/rustc_codegen_llvm/debuginfo/metadata/enums/index.html)). The sidecar adds one field to every value: its `OwnershipState`.

### The index comes in two phases, and only the second needs instruction-level work

rr's trace holds only nondeterministic inputs; `memWrites` are "Userspace writes performed by this event", so every ordinary store must be recomputed by replay ([rr_trace.capnp#L342-L343](https://github.com/rr-debugger/rr/blob/ca20dcb/src/rr_trace.capnp#L342-L343)). **Phase A** is breakpoint-only and cheap, SteamDrill-style: function entries and exits give the call tree, line-table breakpoints give line hits, allocator entry points give heap lineage (realloc creates a successor edge), and named semantic call sites such as cadabra3's trace emitters give anchors ([SteamDrill, OSDI '22](https://www.usenix.org/system/files/osdi22-quinn.pdf); [notes dynamic-provenance.md:418-421](#n-dp)). The allocator shim symbol names were not verified and vary with `#[global_allocator]` and LTO ([notes dynamic-provenance.md:379-380](#n-dp)). **Phase B** is the per-instruction last-writer log for chosen windows. Upstream rr already offers a path: `rr rerun --export-checkpoints` forks clones at an event for parallel shard workers, and `--singlestep=ip,gp_x16,...` dumps registers per step ([RerunCommand.cc#L28-L57](https://github.com/rr-debugger/rr/blob/ca20dcb/src/RerunCommand.cc#L28-L57)); memory writes come from decoding each instruction with `iced-x86` and computing its effective address ([notes rr-internals.md:190-194](#n-rr)). Single-stepping costs "roughly 1000x" ([HN 15427799](https://news.ycombinator.com/item?id=15427799)), about 3 CPU-hours for a 10 s program, which is tolerable only for windows ([notes rr-internals.md:195](#n-rr)). The faster route is a "remix-lite": an emulator (icicle, Rust, MIT/Apache) seeded from rr state, applying recorded `memWrites` at syscalls, counting conditional branches in software and cross-checking registers against rr at every frame, which is how Pernosco's closed-source remix works ([rr remix](https://robert.ocallahan.org/2020/12/rr-remix-efficient-replay-only-binary.html); [icicle-emu](https://github.com/icicle-emu/icicle-emu); [notes dynamic-provenance.md:193-215](#n-dp)). Nobody has published such a bridge, and icicle's AVX coverage is unverified ([notes dynamic-provenance.md:189-190, 225-226](#n-dp)).

Storage follows CodeTracer's one good speed idea and its file format: seekable chunks with a 16-byte header carrying the first event id, and an interval-coverage table so any expensive re-execution happens once and is persisted ([runtime_tracing chunked.rs](https://github.com/metacraft-labs/runtime_tracing/blob/1f322ca8764a32788226707fb6218d2fc4c5f095/codetracer_ctfs/src/chunked.rs); [CodeTracer materialization_cache.rs](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/src/db-backend/src/ctfs_trace_reader/materialization_cache.rs)). hopper keys chunks by `Moment`, writes them in a directory beside the rr trace (never inside it), and keeps the catalogue in redb ([crates.io redb](https://crates.io/crates/redb)). Background work runs on background replicas so it never moves the user's cursor, the opposite of CodeTracer's flow preloader, which drives the user-facing replay ([notes existing-frontends.md:204-205](#n-ef)).

### The GUI stack exists, but three widgets need upstream work

skelter is svelters' own retained toolkit on wgpu, defaulting to winit on Linux ([svelters run.rs:3-8](file:///home/user/svelters/crates/skelter/src/run.rs)). Its `skelter-canvas` already holds "millions of primitives in `f64` world coordinates" with per-chunk level of detail, compositor pan and zoom and an overlay plane, which fits a scrubbable timeline keyed on event or tick ([skelter-canvas lib.rs:1-21](file:///home/user/svelters/crates/skelter-canvas/src/lib.rs)). The two-axis virtual `table` with a Rust `RowModel` suits locals, memory and query results ([table/mod.rs:1-22](file:///home/user/svelters/crates/skelter-widgets/src/table/mod.rs)). berth gives docking through `skelter_berth`'s `PaneHost` seam, which cadatomic already uses ([skelter_berth lib.rs:1-19](file:///home/user/berth/crates/skelter_berth/src/lib.rs)), and quire's `skelter_quire` gives a read-only source view with `reveal` and inlay hints usable for inline values ([skelter_quire editor.rs:723](file:///home/user/quire/crates/skelter_quire/src/editor.rs); [quire-core inlay_hints.rs:118](file:///home/user/quire/crates/quire-core/src/inlay_hints.rs)). Three gaps remain. The tree view re-flattens and clones every visible label on each expand, so a call tree with 10^6 rows needs a `RowModel`-style lazy tree ([tree.rs:206-238](file:///home/user/svelters/crates/skelter-widgets/src/views/tree.rs)); quire has no host-defined gutter for hit counts or an execution arrow and no whole-line highlight ([skelter_quire scene.rs:444-521](file:///home/user/quire/crates/skelter_quire/src/scene.rs)); and quire-syntax has **no Rust grammar** ([quire-syntax Cargo.toml](file:///home/user/quire/crates/quire-syntax/Cargo.toml)). These are other repositories' code, so they go as requests to the svelters coordinator and quire's owner. Two cautions: svelters' newest refactor merges landed while GitHub Actions was down and are CI-unverified, and `skelter_berth` was never run on screen when it landed and takes skelter by `branch = "master"`, so hopper must pin it ([svelters STATUS.md:292-327](file:///home/user/svelters/STATUS.md); [berth SKELTER-BERTH.md](file:///home/user/berth/docs/SKELTER-BERTH.md); [notes gui-stack-and-cadabra.md:139-154](#n-gui)). The default layout should look like an ordinary debugger (source, stack, locals, timeline) with query features one gesture away, because Pernosco's unfamiliar UI makes "some people bounce off it" ([DEBT 2024](https://robert.ocallahan.org/2024/10/debt-workshop.html)).

### MCP and DAP are thin adapters with typed moments

The rr MCP servers surveyed expose up to 48 gdb verbs and treat time as rr's `when` text ([rr-mcp server.py](https://github.com/jnjaeschke/rr-mcp/blob/b10c323042ece18439fce48a1803318f85174b4d/src/rr_mcp/server.py)). `hopper-mcp` should expose about thirteen typed tools (`recording_info`, `processes`, `seek`, `step`, `run_until`, `stack`, `eval`, `memory`, `calls`, `line_hits`, `value_history`, `last_write`, `origin`), each returning JSON with explicit `moment` fields and an ownership layer on `origin` hops ([notes existing-frontends.md:287](#n-ef)). `hopper-dap` maps standard requests plus `stepBack`/`reverseContinue` ([DAP specification](https://microsoft.github.io/debug-adapter-protocol/specification)) and puts omniscient queries in `hopper/*` requests that return their payload **in the response**, with string-tagged JSON and a protocol version in the handshake, unlike CodeTracer's side-channel events ([CodeTracer ct-dap.md](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/ct-dap.md)). A position URL (`hopper://<trace-uuid>/<frame_time>.<tid>.<ticks>.<sub>`) shared by GUI, CLI and agents is the sharing primitive every vendor converged on (prior report:44).

## Recording runs only on PMU hosts, so experiments come before code

rr needs a working retired-conditional-branch counter. **This environment is a Firecracker microVM with no `cpu` PMU device; rr 5.10.0 installs, and `rr record /bin/true` fails with "Unable to open performance counter"** ([notes rr-internals.md:216-226](#n-rr)). Bare-metal Intel works, AMD Zen needs the SpecLockMap workaround after every boot, GCE exposes a PMU only on C4/C4A/M4/A4X with `--performance-monitoring-unit`, AWS only on some large sizes, and Xen and VirtualBox never ([rr wiki: Zen](https://github.com/rr-debugger/rr/wiki/Zen); [GCE: Enable the PMU](https://docs.cloud.google.com/compute/docs/enable-pmu-in-vms); [rr #1753](https://github.com/rr-debugger/rr/issues/1753)). The split of work follows: **cloud lanes build the crates, unit-test the RSP client against recorded packet transcripts, test the evaluator against core-dump-style memory snapshots, and build the GUI; recording, replay and every exit test above run on the user's machine or a PMU-capable server.** The rented daily-check server's PMU support is unknown and must be checked. A remix-like emulator would eventually let replay-side analysis run without a PMU, but upstream rr replay still needs the counter ([notes rr-internals.md:267](#n-rr)).

Eight experiments come first. **E1** runs `rr record true` and `perf stat -e br_inst_retired.conditional true` on the user's machine, the rented server and one cloud container, to fix where hopper can run ([rr wiki](https://github.com/rr-debugger/rr/wiki/Will-rr-work-on-my-system)). **E2** is a spike RSP client that drives `rr replay -s 0`, issues `vRun` seeks, `bc`, `bs` and `qRRCmd:when-ticks`, and measures seek and reverse-step latency, since no source gives a measured figure ([notes rr-internals.md:84](#n-rr)); it also checks whether TLS lookup and shared-library lists work without gdb ([notes existing-frontends.md:292](#n-ef)). **E3** builds the worked example with a `rustc_plugin` driver on `nightly-2026-05-01`, dumps the per-instance events from optimised MIR, and joins them by hand to `addr2line` output, checking whether rustc emits line-table columns, which decides disambiguation precision ([notes rust-static-provenance.md:170](#n-rsp)). **E4** measures sidecar size and build-time cost on one cadabra3 crate ([notes rust-static-provenance.md:171](#n-rsp)). **E5** measures phase-A cost: replay speed with about 10^5 breakpoints, for which no figure exists ([notes dynamic-provenance.md:444](#n-dp)). **E6** emulates one recorded corpus case frame by frame with icicle, comparing registers with rr at each frame and timing it ([notes dynamic-provenance.md:441-443](#n-dp)). **E7** times `rr rerun --singlestep` over a window to calibrate the 1000x estimate. **E8** records a `parasolid-rs` Wine test under rr with `WINELOADERNOEXEC=1`, which in 2025 still needed Wine MR 7669 to avoid a "partial write" error ([wine-gitlab 2025-04](https://list.winehq.org/hyperkitty/list/wine-gitlab@list.winehq.org/message/JM6VNYCPXAJXC2B4QYHMZMSH2CH4IXFN)); Windows PE code then appears as anonymous mappings that need hopper's own PE/PDB support ([notes rr-internals.md:288](#n-rr)).

The risks, most dangerous first: **PMU availability** confines recording to specific machines; **toolchain coupling** means every release of `rustc_plugin` forces a nightly bump, and the user's toolchain is rustc 1.97 while `rustc_plugin` 0.15 pins 1.96 ([rustc_plugin README](https://github.com/cognitive-engineering-lab/rustc_plugin)); **optimised Rust** loses variables and moves, so release-build labels degrade ([Rust-Pernosco slides](https://robert.ocallahan.org/assets/images/Rust-Pernosco.pdf)); **index cost** is unmeasured, and instrumentation must not perturb rr's tick counter, which is why remix counts branches itself ([Exploiting precognition](https://robert.ocallahan.org/2020/12/exploiting-precognition-in-binary.html)); **rr interface drift**, since replies are free text and traces are incompatible across versions; **runtime gaps**, since rr fakes `ENOSYS` for `io_uring_setup`, `clone3` and `close_range`, and `rdrand` fails on Zen ([record_syscall.cc#L4773-L4782](https://github.com/rr-debugger/rr/blob/ca20dcb/src/record_syscall.cc#L4773-L4782)); **GUI dependencies** that are CI-unverified or never run on screen; **scope creep in the evaluator**, the cliff on which rr's Rust port `rd` stalled at about 60,000 lines (prior report:62); and **CodeTracer** shipping an open rr backend, which its AGPL licence and proprietary worker currently prevent ([CodeTracer CHANGELOG.md](https://github.com/metacraft-labs/codetracer/blob/d29c0743b755bef5452f9dc4233f0e4a3deac50e/CHANGELOG.md)).

Six decisions belong to the user rather than to a coordinator. The first is **hopper's licence**, constrained by berth having none yet and by any code vendored from BugStalker (MIT) or Rust's providers (MIT/Apache) ([berth README](file:///home/user/berth/README.md)). The second is **the toolchain policy**: accept a pinned nightly for sidecar builds of recorded programs, or ship without ownership labels on stable. The third is **where recording runs**, including any paid PMU-capable cloud instance. The fourth is **whether recordings containing Parasolid DLL memory may leave the user's machines**, which the existing no-redistribution rule says they should not (prior report:88). The fifth is whether hopper may **depend on unreleased svelters, berth and quire code** and send them the three widget requests. The sixth is whether to ask cadabra3 for a **serialised decision-event stream**, which is a cadabra3 change during its refactor freeze.

## Conclusion

The research shifts hopper's centre of gravity. Recording, reverse stepping and even machine-level copy-following are known quantities; Pernosco, CodeTracer and rr itself have shown each. What none of them can say is *what the program meant* by a copy: whether bytes were moved, cloned, borrowed or dropped, and whether a variable on screen is still alive. That knowledge exists only inside rustc for a few milliseconds per function, and hopper's real invention is to catch it at build time and carry it to replay. The price is a hard coupling between the recorded binary and one nightly toolchain, so the sidecar has to be an optional layer over a debugger that already works without it, which is exactly why the milestones put it fifth.

The second shift is practical: hopper's development environment and its runtime environment differ. Most of the code can be written and unit-tested in PMU-less containers, but no exit test can pass there. The project should therefore treat a recorded-fixture corpus, made once on a PMU host and replayed on the same host for every milestone gate, as infrastructure on day one, and treat E1 and E3 as the two results that decide whether this plan survives contact with real hardware and a real rustc.
